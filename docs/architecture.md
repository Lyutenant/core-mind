# CoreMind Architecture Notes

Detailed design notes and invariants for each subsystem. [`AGENTS.md`](../AGENTS.md) carries a
one-line summary of each and links here; read the relevant section before changing that
subsystem, and update it in the same change when the behavior changes.

## Device auto-selection

Files: `device_cache.py`, `audio_input/devices.py`, `vision/camera_select.py`

- Mic/speaker/camera are selected by **stable name, not enumeration index**, so the same physical device is reused after a USB-topology change (powered hub, replug) or reboot — indexes shuffle, names don't.
- When `audio.input_device` / `audio.output_device` / `vision.camera_index` + `vision.camera_device` are `null` (or `"auto"`), `resolve_input_device` / `resolve_output_device` (audio) and `resolve_camera_source` (camera) auto-pick: audio prefers a USB device (and de-prioritizes a webcam's built-in mic), camera prefers a `/dev/v4l/by-id/*-video-index0` path. The pick is logged once at startup and cached in `~/.coremind/device-cache.json` (`device_cache.remember`), so subsequent boots reuse it while present.
- Explicit config **pins** a device and skips auto-selection: an int (PortAudio/V4L index), an audio **name substring** (`sounddevice` matches it natively), or a camera `/dev/...` path (`cv2.VideoCapture` accepts a path string). `coerce_device` collapses numeric strings (`"1"`→`1`) so env-var/YAML values aren't mistaken for names. `AudioConfig.input_device/output_device` are `Optional[int|str]`; `VisionConfig.camera_index` is `Optional[int]`, `camera_device` is `Optional[str]`.
- Resolution happens at construction sites (`_build_voice_loop` in `main.py`, CLI `audio`/`vision` test commands, `camera_capture.init_camera` on the Node). `coremind doctor` reports the resolved mic/speaker. Two identical USB audio products share a name (ambiguous) — pin explicitly to disambiguate. Relates to the physical-layer-on-Node model.

## System prompt and personality

Files: `server/app.py` (`_build_system_prompt`), `voice_loop.py` (standalone)

- The Hub builds the system prompt in `_build_system_prompt(s)` (`server/app.py`), used by both `/v1/process` (voice) and `/v1/chat` (dashboard). The standalone path builds its own in `VoiceLoop._system_messages()` from the `_SYSTEM_PROMPT` constant.
- `app.personality` (free text) is appended as a persona/tone clause when set. Dashboard presets (JARVIS/Witty/Formal/Neutral) are a frontend-only convenience that fill the textarea — the backend only ever stores/sees the resulting string.
- The `user_location` clause warns the LLM that input arrives via speech recognition and that a *nonsense/garbled* word where a place name would go is likely a mis-transcription — fall back to the configured location; a clearly named real place still overrides it. This is one of three STT-garble defenses (see `weather_tool.py`'s optional-location default + coached unknown-location message, and `stt.hotwords` for fixing the mishearing at the source).
- In remote-brain (Node) mode the Hub's `app.personality` governs the persona; the Node's value is only used in standalone mode.

## Voice loop

Files: `voice_loop.py`

- Wake word → VAD record → process → speak → **follow-up window** (`follow_up_seconds`) where the user can continue without the wake word.
- Follow-up safety: stop phrases (`_STOP_PHRASES` — "stop", "goodbye", "that's all", …) end the session; `follow_up_min_words` discards noise fragments; `post_response_cooldown_seconds` suppresses speaker echo. All hot-reloadable from the Nodes panel.
- Playback isolation: when music/ATC is playing, mpv is **terminated** before the turn (freeing the single-open USB speaker for the chime/recording/TTS) and **relaunched** after (`try/finally` guarantees resume). See Node MCP playback for why SIGSTOP doesn't work here.

## Wake confirmation gate

Files: `text_match.py`, `runtime.wake_confirm_words`

- A **post-STT semantic gate** against false wakes (sudden noise, TV dialogue): the **first** utterance after the wake word must END with a configured terminator word (default `["over", "go ahead", "confirm"]`) or the turn is silently discarded — no LLM, no TTS, no reply. Follow-up turns within the same wake cycle do **not** need it; `null`/`[]` disables the gate. It only suppresses false *responses* — the wake chime still fires before recording — so it is **complementary** to wake-threshold / Silero-VAD tuning, not a replacement.
- Matching lives in `coremind/text_match.py::match_and_strip_terminator` (case-insensitive, punctuation-tolerant, longest-phrase-wins; strips the terminator before the LLM sees the text). Shared by both gate sites. An utterance that is *only* the terminator strips to empty → also discarded.
- **Where it runs:** in remote (Node→Hub) mode the Hub's audio is synthesized before the Node ever sees the transcript, so the gate must run on the **Hub** — `/v1/process` after STT, before the LLM. The Node signals the first post-wake turn with the `X-Confirm-Gate: 1` request header; the Hub applies its **own** `runtime.wake_confirm_words` (config ownership mirrors `app.personality`) and on rejection returns an empty body with `X-Rejected: terminator`, which the Node treats as a silent no-op. In **standalone** mode the Node enforces its own config inline in `_process_local_wav`. The gate applies only when a wake word triggered the turn (never push-to-talk / `chat`).

## Tool layer

Files: `tools/`

- Ollama native tool API; the Hub runs a tool loop (max 5 rounds): LLM → execute tool calls → feed results back → repeat until plain content → TTS.
- Built-in tools execute synchronously; MCP tools route through `MCPManager` (`execute_async`). Both appear merged to the LLM.
- `MCPManager` holds one background asyncio task per server with a reconnect loop (exponential backoff 10→60 s). Schemas are re-registered on every reconnect, so Node restarts don't require a Hub restart. Startup order doesn't matter.
- **Transports:** `stdio` (spawn subprocess; optional `env` merged over the SDK's `get_default_environment()`), `http` (SSE — appends `/sse` to `url`; the Node MCP server's transport), `streamable-http` (URL used verbatim, e.g. Home Assistant's `/api/mcp`; needs mcp≥1.8, guarded separately so old installs degrade with an install hint, not a dead MCP layer). `headers`/`env` values support `${VAR}` references, expanded from the Hub's environment **at connect time in `MCPManager`, never inside the Pydantic model** — `GET /api/config` serves a `model_dump()` to the dashboard, so expanding at load would leak the secret to every browser. An undefined variable disables that server at startup (fail closed, clear log) — the process env can't heal by retrying.
- **Home Assistant is a config-only integration:** HA's official core *MCP Server* integration (Streamable HTTP at `/api/mcp`, Bearer long-lived token) exposes the Assist API as tools (`HassTurnOn`, …). Safety boundary = HA's *expose to Assist* entity list (MCP tools bypass `requires_confirmation`) — docs tell users not to expose locks/alarms/garage doors. HA itself runs outside CoreMind (e.g. HA Container on the Pi, alongside the Node — it never opens ALSA); the Hub connects directly, **not** through the Node's FastMCP server. See `docs/tools.md` "Smart Home via Home Assistant".
- **Periodic tool re-sync (`_hold_and_resync`):** while a connection is held open, the Hub re-fetches the server's tool list every `resync_interval` s (default 45) and updates schemas if they changed — so a capability newly enabled on the Node (e.g. flipping `vision.enabled`, which adds `capture_image`) is picked up *without* a Hub restart or a detected disconnect. This also acts as a liveness probe: after `resync_max_failures` (default 3) consecutive failed re-syncs the session is dropped and the reconnect loop takes over, which catches half-open SSE connections a plain hold-open wouldn't notice. `_register_schemas` fetches `list_tools()` **before** clearing the old entries, so a single failed poll never wipes a server's tools; re-sync logs at INFO only when the tool set changes.
- **On-demand refresh:** `MCPManager.refresh()` forces an immediate re-sync of every connected server (returns `{server: tool_count}`, `None` per server on failure). Exposed as `POST /api/tools/refresh` and the dashboard Tools panel's **Sync MCP** button, for when you don't want to wait out the 45 s poll after enabling a Node capability.
- `_get_dispatcher()` in `server/app.py` re-attaches the MCP manager after every config reload so MCP tools survive dashboard saves.
- **MCP result extraction (`_extract_tool_result`):** modern FastMCP (mcp ≥ 1.10) derives an output schema from a tool's return annotation and returns the value as *structured output*. For a non-object return (e.g. a tool typed `-> str` like the Node's `capture_image`), it wraps the value as `structuredContent={"result": <value>}` and the legacy `content` block carries the **JSON-serialized** wrapper — so reading `content` alone yields `{"result": "..."}`, not the raw string (this broke `capture_image`'s base64 JPEG). `call_tool` unwraps the `result` key, but **only when the tool's advertised `outputSchema` is FastMCP's wrapper shape** (`properties == {result}`, checked by `_is_fastmcp_result_wrapper`); genuine structured results (e.g. a `-> dict[str,str]` with an `additionalProperties` schema) pass through verbatim. `_register_schemas` captures each tool's `outputSchema` into `_output_schemas` (scoped per server) for this gate. Known accepted residual: a tool whose real return model has a single field literally named `result` is indistinguishable from the wrapper and gets unwrapped — contrived and cosmetic; documented in the code, deliberately not gated on schema `title`.
- Diagnostics: `GET /api/tools` returns `{total, built_in, mcp, mcp_connected, schemas}`.
- **New tool capabilities go through MCP. Do not invent a parallel tool protocol.**
- **Audio-playing MCPs follow the resolver pattern** — they return a stream URL and the LLM
  plays it via the Node's `play_stream`; they must never spawn their own player on the Node
  (see Node MCP playback).

## Node registration

Files: `server/app.py` + `voice_loop.py`

- Nodes auto-register when `remote_brain.enabled`; heartbeat + config poll every 30 s; Hub marks nodes offline after 90 s. A 404 heartbeat (Hub restarted, in-memory registry lost) triggers automatic re-registration, so a Hub restart never strands a connected Node.
- The Hub Nodes panel hot-reloads wake word / VAD / follow-up params on the Node without restart.
- Overrides persist to `~/.coremind/node-overrides.json` with **latest-wins** logic: whichever changed more recently — the Node's `config.yaml` (mtime) or the Hub's dashboard save — takes effect.

## Sessions

Files: `server/app.py` + `static/index.html`

- A **Session** groups a conversation's rounds under a hash id (`uuid4().hex`). Persisted under `~/.coremind/sessions/` as **one `<id>.json` per session** (full rounds) plus a lightweight **`index.json`** (active pointer + per-session metadata — `title`, timestamps, `round_count` — **no rounds**). All writes go through `_atomic_write_json` (`tempfile` + `os.replace`), since this is durable data. A turn (`_append_round`) rewrites only its own session file + the tiny index, **not** the whole history; `_set_active` writes the index alone. `_save_sessions` (full flush of every file + index) survives only for migration/tests. Caps: 50 sessions, 200 rounds/session (`_prune_sessions` also unlinks dropped session files). Loaded once at import (`_load_sessions`): **the directory is the source of truth** — `_scan_session_files` loads every `<id>.json` (skipping the index, `.tmp` residue, and any foreign/corrupt/mismatched-id file with a warning), the index supplies only the active pointer, and the index is rebuilt when it disagrees with the directory — so a session file copied in by hand, or written just before a crash, still shows up; conversations survive a Hub restart. **Legacy migration:** a pre-existing single-file `~/.coremind/sessions.json` is auto-split into the per-file layout on first load and renamed to `sessions.json.bak` (`_migrate_legacy_sessions`). Consistency: session file is always written **before** the index, so the index never references a missing file; a stale `round_count` self-heals on the next index write (single-process Hub — no locking).
- **Active vs. viewed.** Exactly one session is server-global **active** (`_active_session_id`) — where new voice/chat turns land (`_append_round`). Each dashboard device chooses which session it **views** (`viewedSessionId`, persisted per-browser in `localStorage`). Devices viewing the same session stay in lockstep over SSE.
- **Follow mode.** Each device has `followActive` (default true). On a `session_activated` SSE event (active changed via *New session*, *Activate*, or *Clear*+delete), follow-mode devices auto-switch; a device that manually opened a past session is pinned and shows a **Resume live** control. The frontend filters `turn` events by `session_id` (renders only if it matches the viewed session) and shows the pending/processing card only when `followActive`.
- **Unified voice + chat.** `/v1/process` (voice) and `/v1/chat` (dashboard) both land in the active session, so they share one transcript **and** one LLM memory. `_get_session` rebuilds `SessionMemory` from a session's persisted rounds, so restart-resumed/device-switched conversations keep context. Typing into a viewed past session re-activates it (brings it to front).
- **Endpoints:** `GET/POST /api/sessions`, `GET/DELETE/PATCH /api/sessions/{id}` (PATCH = rename, body `{title}`, whitespace-collapsed, capped at 80 chars via `_rename_session`; a renamed session is never auto-retitled), `DELETE /api/sessions` (bulk, body `{ids:[…]}`, unknown ids ignored), `POST /api/sessions/{id}/activate`. Single and bulk delete share `_delete_sessions(ids)`: repairs the active pointer (survivor, else a fresh persisted session), writes the index once, emits `session_activated` if needed + one `session_list_changed` carrying `deleted: [ids]`. `GET/DELETE /api/conversation` are kept as back-compat for the **active** session. SSE events: `session_activated`, `session_list_changed` (plus `conversation_cleared` carries `session_id`).
- **Sessions view (dashboard):** a top-level **Sessions** tab (sidebar + phone bottom bar) lists every session newest-first with a checkbox, title (click → opens it on the Dashboard; ✎ → inline rename), turn count, last-updated, and ACTIVE/VIEWING badges. Toolbar: select-all, **Empty** (0 turns) / **Older than 30d** quick-selects, Clear, and a **Delete** bulk action (one confirm, calls out the active session if included; deleting everything is allowed — the server creates a fresh one). Any device whose *viewed* session gets deleted elsewhere falls back to the active session (handled in the `session_list_changed` handler). No archive: the JSON files on disk are the archive — copy one back in and the directory-scan loader picks it up.
- **Counts and turn numbers.** A round's `turn` is its **1-based position within its session** (assigned in `_append_round`, carried by the SSE `turn` event); there is no process-global turn counter, and the dashboard renumbers from array position on every `loadSession`, so labels never repeat or wrap after a Hub restart. `/api/health` reports `session_count` = size of the registry (= files on disk) and `active_session_turns`; the dashboard's Stats panel shows **Sessions** = session-list length and **Turns** = round count of the *viewed* session.
- **SSE watchdog (`sseWatchdog`, `resyncSessions` in `index.html`).** The Hub pings every 25 s; a stream that goes quiet for 60 s (Mac sleep, backgrounded tab, proxy drop — `EventSource.onerror` doesn't always fire) is reconnected client-side and the session list/active pointer re-fetched; the same re-sync runs on `visibilitychange` → visible. This is why a device can't stay stuck on a stale dropdown without a manual reload.
- **Config live-sync (not history):** a `config_saved` SSE event now makes other devices re-`loadConfig()` so their Settings form refreshes live (skipped if a Settings field is focused, to avoid clobbering an in-progress edit). Config *history* is deliberately out of scope.

## Vision on demand

Files: `vision/`, `tools/built_in/vision_tool.py`, `node_mcp/tools/camera_capture.py`

- The camera is a **Node** capability (physical layer on the Pi, like mic/speaker); inference runs on the **Hub**. The Pi does cheap I/O (grab a frame); the Mac runs the vision model.
- Flow: LLM calls the built-in `look` tool → `look` fetches a frame from the Node via `capture_image` (MCP) → runs the Hub's local Ollama vision model (`ollama.vision_model`) → returns **plain text**. The image never travels through the generic LLM tool-result path, so the text-only tool loop is unchanged.
- `look` overrides `Tool.run_async` (async) because it awaits an MCP call; the vision inference runs in a thread (`asyncio.to_thread`) so it doesn't block the event loop. `capture_image` is hidden from the LLM via `LookAtSceneTool.wraps_mcp_tools` (the dispatcher filters wrapped MCP tools out of the advertised schemas) so the model never sees raw base64.
- Privacy: images are held in memory only, never written to disk (except `coremind vision test`, which the user explicitly requests); logs record metadata only. Vision is local-only — never add a silent cloud fallback. The `look` tool is **opt-in** (needs `ollama.vision_model` + `look` in `tools.built_in` + the Node's `vision.enabled`).
- **Dashboard snapshot** (`POST /api/vision/capture`, `POST /api/vision/describe` in `server/app.py`; Camera card in `static/index.html`): the dashboard can grab a still from the Node webcam and display it, with an optional "Describe this" button that runs the Hub vision model on that exact frame. `capture` calls `dispatcher.execute_async("capture_image", {})` directly and returns a `data:image/jpeg;base64,…` URL — `capture_image` stays blocked from `/api/tools/invoke` (which 403s MCP tools), so these are dedicated routes. A raw snapshot needs only the Node's `vision.enabled` (no `vision_model`); only **describe** needs `ollama.vision_model`. `describe` is stateless — the browser posts the displayed base64 back, so it describes the frame on screen. Same privacy posture as `look`: in-memory only, never written to disk, base64 never logged. This is purely on-demand — it does **not** add any push-to-Node, scheduler, or continuous-capture path (that's roadmap rung 6). The JPEG validator `looks_like_jpeg_base64` (`tools/built_in/vision_tool.py`) guards both `look` and these endpoints.

## Node MCP playback

Files: `node_mcp/playback.py`

- One shared mpv process slot: starting music stops ATC and vice versa; pause/resume covers whichever source is active.
- **Voice-turn isolation = terminate + relaunch, not SIGSTOP.** The USB speaker allows only one ALSA open at a time, and a `SIGSTOP`-suspended process keeps the device handle — so a frozen mpv blocks the wake chime and the TTS reply (`PaErrorCode -9985`). `pause()` therefore fully terminates mpv (freeing the speaker) and `resume()` relaunches the stored command. `resume()` is a no-op if the turn itself stopped or started playback (a stop/play tool call), tracked via `_paused`/`_current_cmd`. Live ATC relaunches cleanly; music relaunches from the start (position-restore is a deferred follow-up).
- The wake chime plays **after** `_on_listening_start()` in `voice_loop.run_once`, so it isn't fighting an active stream for the output device.
- **Resolver pattern (`play_stream`):** external audio MCPs must never spawn their own player on the Node — a foreign mpv holds the single-open speaker outside `pause()`/`resume()`, muting the chime/TTS. They *resolve* instead: their tools return a ready-to-play http(s) `url`, and the LLM chains it into the generic `play_stream(url, title)` tool (`music_player.play_stream`), which feeds this shared slot — voice-turn isolation, `stop_playback`, and one-source-at-a-time then cover any stream automatically. `play_stream` validates the scheme (http/https, no whitespace), never echoes the URL back (it would be spoken), and is always registered. `node_mcp.atc_enabled: false` hides the 4 built-in catalog ATC tools so an external ATC resolver MCP (e.g. a streamable-http server on the Pi running in a no-playback resolver mode) is the LLM's only ATC path.

## ATC channel selection

Files: `node_mcp/atc_catalog.py`

- A query that names an airport but no channel type defaults to **tower**; explicit types (ground, atis, ops, …) override.
- When multiple tower channels at one airport tie (per-runway towers), one is picked at random from **primary** feeds only — backup/temp/secondary/TCA/helicopter/emergency feeds are never auto-picked (`_NON_PRIMARY_TOWER_TOKENS`). Non-tower ties, or tower ties with no primary feed, return a disambiguation list.
- An explicit VHF frequency in the query ("tower 120.250") is the strongest channel signal — matched against the catalog `freq` field, channel name, and the mount's dot-stripped encoding. Frequency and channel-name bonuses are scoped to the named airport (a reused frequency must never pull in another airport's channel); queries containing a frequency are never resolved by random pick, and a winning channel that doesn't confirm the requested frequency is refused with the closest match (`matches_query_frequency`), never streamed silently.
- **The ATC stream provider's domain must never appear in user-facing output, docs, or comments.** The URL literals exist only in `atc_catalog.py` (`stream_url` / `pls_url`) — always build URLs through those helpers.
